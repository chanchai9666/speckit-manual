1. สรุปภาพรวม & แนวคิด Spec-Driven Development (SDD)

Spec Kit เป็นชุดเครื่องมือโอเพนซอร์สจาก GitHub ที่ช่วยยกระดับการทำงานกับ AI Coding Agent จากการเขียนโค้ดแบบเดาสุ่ม (vibe coding) มาสู่กระบวนการที่รัดกุมผ่านแนวคิด Spec-Driven Development (SDD) โดยเปลี่ยน Specification ให้กลายเป็นสิ่งที่ “ตรวจสอบได้ (Executable)” และเป็นพิมพ์เขียวที่ AI ใช้สร้างโค้ดตามลำดับ

3 กระบวนการอิสระของ Spec Kit

เป้าหมายกระบวนการคำสั่งหลักผลลัพธ์ที่ได้
สร้างฟีเจอร์ / แอปใหม่ Spec-Driven Development (Core) /speckit.specify → plan → tasks → implement → converge spec.md, plan.md, tasks.md และซอร์สโค้ด
วิเคราะห์และซ่อมบั๊ก Bug Fixing (Bundled Extension) /speckit.bug.assess → fix → test assessment.md, fix.md, test.md (ยืนยันผล verified)
ประเมินความคุ้มค่าของไอเดีย Idea Assessment (Bundled Extension) /speckit.assess.intake → research → define → shape → decide Verdict: go / needs-clarification / kill
หลักการสำคัญ: SDD อยู่ใน Core และใช้งานได้ทันทีหลัง specify init ส่วน Bug Fixing และ Idea Assessment เป็น Extension เสริมที่ติดตั้งเพิ่มเมื่อต้องการใช้งาน

2. ข้อกำหนดเบื้องต้น & การติดตั้ง (Installation)

ข้อกำหนดของระบบ

  • Python 3.11 ขึ้นไป
  • uv (แนะนำอย่างยิ่งสำหรับจัดการเครื่องมือ Python) หรือ pipx
  • ระบบปฏิบัติการ: Linux, macOS, Windows (รองรับ PowerShell โดยตรง ไม่จำเป็นต้องใช้ WSL)
  • AI Coding Agent ที่รองรับ (GitHub Copilot, Claude Code, Opencode, Codex CLI, Gemini CLI, Qwen ฯลฯ)
  • Git — ไม่บังคับ (ต้องการเฉพาะเมื่อเปิดใช้ git extension)

วิธีการติดตั้ง CLI

bash
# ติดตั้งด้วย uv (แนะนำ รวดเร็วและแยกสภาพแวดล้อมอัตโนมัติ)
uv tool install specify-cli

# หรือติดตั้งด้วย pipx
pipx install specify-cli

# ติดตั้งเวอร์ชันเจาะจง
uv tool install specify-cli==0.12.11

# ติดตั้งจาก GitHub Repository โดยตรง (ระบุ release tag)
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@vX.Y.Z

# ใช้งานครั้งเดียวโดยไม่ต้องติดตั้งลงเครื่อง (uvx)
uvx --from git+https://github.com/github/spec-kit.git@vX.Y.Z specify init --here --integration copilot

ตรวจสอบความพร้อมหลังติดตั้ง

bash
specify version      # ตรวจสอบเวอร์ชัน CLI, Python, แพลตฟอร์ม
specify check        # ตรวจสอบว่าเครื่องมือของ AI Agent มีพร้อมในระบบ
specify self check   # ตรวจสอบว่ามี CLI เวอร์ชันใหม่ออกมาหรือไม่ (read-only)

3. คำสั่ง 2 ประเภท (CLI vs Agent)

สิ่งที่ผู้เริ่มต้นมักสับสนคือการแยกระหว่าง คำสั่งใน Terminal กับ คำสั่งในหน้าแชทของ AI ซึ่งต้องแยกให้ชัดเจนตั้งแต่เริ่มแรก:

1. CLI Commands (Terminal)

รันใน Command Prompt / Terminal ใช้สำหรับเตรียมโปรเจค, สลับ Agent, ติดตั้ง Extensions และอัปเกรดเครื่องมือ

bash
specify init my-project
specify integration switch claude
specify extension add bug
specify self upgrade

2. Agentic Commands (Chat / Skill)

พิมพ์ใน ช่องแชทของ AI Coding Agent เป็น Slash Command หรือ Skill เพื่อควบคุมกระบวนการสร้างโค้ด

text
/speckit-specify
/speckit-plan
/speckit-implement
/speckit-converge

รูปแบบการเรียกคำสั่งตาม AI Agent

4. เริ่มต้นโปรเจคใหม่แบบด่วน (Quick Start)

  1. ติดตั้ง CLI ครั้งเดียวต่อเครื่อง
    bash
    uv tool install specify-cli
  2. สร้างโฟลเดอร์โปรเจคและกำหนด AI Agent
    bash
    specify init my-project --integration copilot
cd my-project
    สำหรับการรันบน CI หรือ Script ให้ใส่ --non-interactive และ --script sh (หรือ ps บน Windows)
  3. เปิดโฟลเดอร์โปรเจคใน AI Agent แล้วรันคำสั่งตามลำดับ
    text
    /speckit-constitution  กำหนดหลักการพื้นฐานและมาตรฐานคุณภาพ (ทำครั้งเดียว)
/speckit-specify       อธิบายว่าต้องการสร้างอะไรและเพราะอะไร (What & Why)
/speckit-clarify       ตอบคำถามเพื่อลดความกำกวมในข้อกำหนด
/speckit-plan          กำหนด Architecture, Framework และ Database (Tech Stack)
/speckit-checklist     ตรวจสอบความพร้อมของ Requirement
/speckit-tasks         แตกงานย่อยและจัดลำดับ Dependency
/speckit-analyze       ตรวจความสอดคล้องระหว่าง Spec, Plan และ Tasks (Read-only)
/speckit-implement     ลงมือเขียนโค้ดตาม Tasks
/speckit-converge      ตรวจสอบความครบถ้วนเทียบกับ Spec
  4. ทำซ้ำ implement → converge จนกว่าจะได้ผลลัพธ์เป็น Converged จากนั้นจึงเริ่มทดสอบและเปิด Pull Request
ข้อควรจำ: specify init ทำเพียงครั้งเดียว คำสั่งและเทมเพลตจะถูกติดตั้งถาวรในโฟลเดอร์ .specify/ และโฟลเดอร์ของ AI Agent

5. ลำดับขั้นตอนการทำงาน (Workflow Order): แบบเต็ม vs แบบย่อ

หัวใจสำคัญของ Spec-Driven Development (SDD) คือการเปลี่ยนกระบวนการคิดให้มีขั้นตอนที่เป็นระบบ เพื่อให้ AI ทำงานได้อย่างแม่นยำ ไม่หลงทาง และมีหลักฐานตรวจสอบย้อนกลับได้ คุณสามารถเลือกลำดับขั้นตอนให้เหมาะกับขนาดและความเสี่ยงของงานได้ 3 รูปแบบหลัก:

🛡️ เส้นทางเต็ม (Full Production Workflow) — สำหรับงานระบบหลักและ Production 4 Quality Gates ครบถ้วน

ลำดับวงจรการพัฒนาแบบสมบูรณ์ มีจุดตรวจสอบคุณภาพ (Quality Gates) ทุกระยะเพื่อป้องกันข้อผิดพลาดทางสถาปัตยกรรมและ Logic Drift:

1. constitution→ 2. specify→ 3. clarify 🔍→ 4. plan→ 5. checklist 📋→ 6. tasks→ 7. analyze 🔬→ 8. implement→ 9. converge 🎯

🔍 4 ด่านตรวจคุณภาพ (Quality Gates) ในแบบเต็ม

  • Gate 1: Clarify — ซักถามเจาะลึก 3-5 ข้อเพื่อกำจัดจุดคลุมเครือในข้อกำหนดก่อนเริ่มวางแผน
  • Gate 2: Checklist — สร้างเกณฑ์ตรวจความพร้อมของสเปกโดยมนุษย์ต้องเป็นผู้ Sign-off ก่อนลงมือแตกงาน
  • Gate 3: Analyze — ตรวจจับ Drift ข้ามเอกสาร (spec vs plan vs tasks) โดยไม่อ่านหรือแก้โค้ด
  • Gate 4: Converge — ตรวจความครบถ้วนสมบูรณ์ของโค้ดเทียบกับสเปกแบบ Append-only ก่อนเปิด PR

🎯 เหมาะสำหรับสถานการณ์ใด?

  • โปรเจคใหม่ตั้งแต่ศูนย์ (Greenfield 0-to-1)
  • ฟีเจอร์หลัก (Core Architecture / Business Domain)
  • ระบบที่มีความสำคัญสูง เช่น ระบบชำระเงิน, ความปลอดภัย, หรือ Authentication
  • งานที่ต้องส่งมอบในทีมขนาดใหญ่ที่มี Code Reviewer หลายคน
⚡ เส้นทางย่อ (Compact / Fast-Track SDD) — สำหรับฟีเจอร์ย่อยและงานต่อยอด กระชับ รวดเร็ว ตรงจุด

วงจรการพัฒนาแบบตัดทอนขั้นตอนที่ไม่จำเป็นออก เน้นความเร็วในการส่งมอบงาน แต่ยังคงรักษากระบวนการ Spec-First เอาไว้ครบถ้วน:

1. specify→ 2. plan→ 3. tasks→ 4. implement→ 5. converge 🎯

✂️ ข้ามขั้นตอนใดได้บ้าง และเพราะอะไร?

  • ข้าม constitution — เนื่องจากมีกฎระเบียบกลางบันทึกอยู่ใน .specify/memory/constitution.md อยู่แล้ว
  • ข้าม clarify — เมื่อผู้พัฒนาและทีมมี Requirement และภาพ UI/Mockup ที่ชัดเจน ไม่มีจุดกำกวม
  • ข้าม checklist & analyze — เหมาะกับงานขนาดเล็กถึงปานกลางที่ไม่มีความซับซ้อนข้ามเซอร์วิส

⚠️ สิ่งที่ห้ามข้ามในแบบย่อ

  • ห้ามข้าม specify — AI ต้องเข้าใจ "ปัญหาและผลลัพธ์ที่ต้องการ (What & Why)" ก่อนเสมอ
  • ห้ามข้าม tasks — ต้องแตกงานเป็นขั้นตอนเล็กๆ เพื่อป้องกัน AI เขียนโค้ดแบบสุ่มหรือตกหล่น
  • แนะนำให้รัน converge — เพื่อให้แน่ใจว่างานที่ทำเสร็จครบตาม Scope ย่อจริง
🔥 เส้นทางด่วนพิเศษ (Express / Hotfix Path) — สำหรับงานแก้ด่วนและจุดเล็กๆ Speed Priority

สำหรับงานแก้บั๊กจุดเดียว, การเปลี่ยนข้อความ, หรือการปรับแต่งสไตล์ที่ไม่แตะต้องโครงสร้างสถาปัตยกรรม:

1. specify (สั้น)→ 2. tasks (1-3 ข้อย่อย)→ 3. implement→ 4. converge
ข้อควรระวังของ Express Path: ใช้เฉพาะเมื่อ ไม่เปลี่ยน Tech Stack, ไม่เพิ่มตารางในฐานข้อมูล และไม่แก้ API Contract เดิม หากงานเริ่มบานปลาย ให้ถอยกลับไปใช้แบบย่อหรือแบบเต็มทันที

ตารางเปรียบเทียบกระบวนการ: แบบเต็ม vs แบบย่อ (Workflow Comparison Matrix)

ลำดับ & ขั้นตอน คำสั่ง Agent Slash แบบเต็ม (Full) แบบย่อ (Compact) ไฟล์ผลลัพธ์ (Artifacts) หน้าที่หลัก & จุดตรวจสอบ (Role & Gates)
1. Constitution /speckit-constitution จำเป็น (ครั้งแรก) ใช้ของเดิม .specify/memory/constitution.md ตั้งกฎเหล็กของโปรเจค เช่น Coding Standards, Testing Policy, Constraints
2. Specify /speckit-specify จำเป็น จำเป็น specs/<feature>/spec.md ระบุ What & Why พฤติกรรมผู้ใช้ และขอบเขต (ห้ามใส่ Tech Stack)
3. Clarify /speckit-clarify Quality Gate 1 ข้ามได้ถ้าสเปกชัด อัปเดตลงใน spec.md AI ถามเจาะลึก 3-5 ข้อเพื่อกำจัดจุดคลุมเครือและบันทึกคำตอบกลับลงสเปก
4. Plan /speckit-plan จำเป็น จำเป็น specs/<feature>/plan.md กำหนดสถาปัตยกรรม, Tech Stack, Database Schema และ API Contracts
5. Checklist /speckit-checklist Quality Gate 2 ข้ามได้ specs/<feature>/checklists/ Human Sign-off ยืนยันว่า Requirements ผ่านเกณฑ์และอนุมัติให้เริ่มพัฒนา
6. Tasks /speckit-tasks จำเป็น จำเป็น specs/<feature>/tasks.md แตกรายการงานย่อยตามลำดับ Dependency: Setup → Foundation → Stories → Polish
7. Analyze /speckit-analyze Quality Gate 3 ข้ามได้ Read-only Drift Report ตรวจสอบความสอดคล้องข้ามเอกสาร spec vs plan vs tasks (ไม่อ่าน/แก้โค้ด)
8. Implement /speckit-implement จำเป็น จำเป็น Source code, Tests & Diffs AI ลงมือเขียนโค้ดและ Unit Tests ตามลำดับใน tasks.md ทีละช่วง
9. Converge /speckit-converge Quality Gate 4 แนะนำอย่างยิ่ง Tasks appended หรือ Done ตรวจเทียบโค้ดจริงกับสเปกแบบ Append-only เพิ่ม tasks ที่ตกหล่นจนครบถ้วน
10. Issues (Opt) /speckit-taskstoissues ส่วนเสริม ส่วนเสริม GitHub Issues บน Repo แปลงรายการงานใน tasks.md ให้เป็น GitHub Issues เพื่อติดตามงานบน Projects

เกณฑ์การตัดสินใจ: เมื่อไหร่ควรใช้แบบเต็ม vs แบบย่อ?

🛡️ เลือกใช้ "แบบเต็ม" เมื่อ:

  • งานมีผลกระทบต่อโครงสร้างข้อมูลหรือโมเดลความปลอดภัย
  • ฟีเจอร์มีความสัมพันธ์แบบผูกโยงกับหลายระบบ (Cross-module Dependency)
  • ความต้องการจาก Product Owner ยังไม่นิ่ง หรือมี Edge Cases ซับซ้อน
  • ทีมต้องการ Audit Trail และเอกสาร Checklist สำหรับการตรวจรับงาน

⚡ เลือกใช้ "แบบย่อ" เมื่อ:

  • เพิ่มหน้า UI ย่อย, แบบฟอร์ม หรือคอมโพเนนต์ที่แยกการทำงานชัดเจน
  • สเปกมีความชัดเจนสูง พร้อม Wireframe หรือ API Contract ที่แน่นอนแล้ว

8. แนวทางปฏิบัติที่ดี (Best Practices)

  1. ตั้ง Constitution ครั้งเดียวแต่ให้ครอบคลุม — ใส่มาตรฐานด้านการทดสอบ คุณภาพโค้ด และข้อจำกัดทางสถาปัตยกรรม
  2. แยก What/Why ออกจาก How อย่างเด็ดขาด — ห้ามใส่ชื่อ Framework หรือ Database ในขั้น specify ให้เก็บไว้ใส่ใน plan
  3. รันทีละขั้นตอนและตรวจทานไฟล์จริง — อ่าน spec.md และ plan.md ก่อนสั่งแตกงานเสมอ
  4. ใช้ Quality Gates กับงาน Production — เพิ่มขั้นตอน clarify, checklist และ analyze
  5. ทำซ้ำ implement → converge จนกว่าจะได้ Converged — ก่อนเปิด PR หรือส่งมอบงาน
  6. Commit งานก่อนการ Init หรือ Upgrade ทุกครั้ง — เพื่อให้สามารถดู Diff ได้ชัดเจน

10. โปรเจคเดิมที่มีอยู่แล้ว (Brownfield)

    bash

  3. ตั้ง Constitution อิงจากมาตรฐานที่มีอยู่จริงของโปรเจค
    text
    /speckit-constitution ห้ามแก้ไข Public API เดิม, คงโครงสร้างโฟลเดอร์เดิม, รันเทสที่มีอยู่เดิมต้องผ่าน 100%
  4. ระบุ Bounded Change สำหรับฟีเจอร์ใหม่
    text
    /speckit-specify เพิ่มระบบ Export รายงานสรุปเป็นไฟล์ Excel ในหน้ารายการสั่งซื้อ โดยใช้สิทธิ์ Authorization เดิม
  5. วางแผนให้เข้ากับระบบเดิมแล้วทำตามกระบวนการ SDD

11. การจัดการ & อัปเดตสเปก (Spec Maintenance Models)

เมื่อซอฟต์แวร์มีการเปลี่ยนแปลง คุณสามารถเลือกรูปแบบการดูแล Spec ได้ 3 แบบตามความเหมาะสม:

1. Flow-Forward Spec (แนะนำ)

แต่ละโฟลเดอร์ใน specs/ คือบันทึกประวัติศาสตร์ของฟีเจอร์นั้น เมื่อมีฟีเจอร์ใหม่ให้สร้าง Spec ใหม่เสมอ

กระบวนการ: /speckit-specify ใหม่ → plan → tasks → implement → converge

2. Living Spec

ไฟล์ spec.md ถือเป็นสัญญาหลัก (Source of Truth) เมื่อ Requirement เปลี่ยน ให้แก้ที่ spec.md ก่อนเสมอ

กระบวนการ: แก้ spec.md → plan ใหม่ → tasks ใหม่ → analyze → implement

3. Flow-Back Spec

เมื่อพบข้อจำกัดใหม่ระหว่าง Implement ให้บันทึก Discovery แล้วย้อนกลับมาปรับปรุง Spec/Plan ให้สอดคล้องกัน

กระบวนการ: บันทึกประเด็นที่พบ → ปรับปรุง spec/plan → analyze → implement ต่อ

เมื่อสลับ Integration ไฟล์ที่มีการแก้ไขด้วยตนเองจะถูก เก็บรักษาไว้ โดยจะเขียนทับเฉพาะไฟล์ managed ที่ไม่มีการเปลี่ยนแปลงเท่านั้น

18. Git Extension & Automation

Spec Kit ไม่บังคับให้ต้องใช้ Git ในการทำงาน แต่หากต้องการให้จัดการ Branch และ Commit ให้อัตโนมัติ สามารถเปิดใช้งาน Git Extension ได้:

bash
specify extension add git

ไฟล์การตั้งค่าจะอยู่ที่ .specify/extensions/git/git-config.yml

yaml
# ตัวอย่างการตั้งค่า .specify/extensions/git/git-config.yml

branch_template: ""                # รูปแบบชื่อ branch (เช่น {author}/{number}-{slug})
init_commit_message: "[Spec Kit] Initial commit"
commit_style: fixed                # fixed หรือ conventional commits
auto_commit:
  default: false                   # commit อัตโนมัติหรือไม่
  after_specify:
    enabled: true
    message: "[Spec Kit] Add specification"

20. Environment Variables ที่สำคัญ

ตัวแปรสภาพแวดล้อมหน้าที่และการใช้งาน
SPECIFY_FEATURE_DIRECTORYระบุโฟลเดอร์ฟีเจอร์ปัจจุบันโดยตรง (ข้าม feature.json) เช่น specs/001-my-feature
SPECIFY_INIT_DIRชี้ตำแหน่ง Root ของโปรเจคเมื่อรันคำสั่งจากโฟลเดอร์อื่น
SPECIFY_FEATURE_NO_PERSIST=1ห้ามเขียนไฟล์ feature.json เมื่อรันหลาย Agent พร้อมกัน
SPECKIT_INTEGRATION_DEFAULTกำหนด Agent เริ่มต้นสำหรับการทำ specify init บน CI
SPECIFY_UPGRADE_TIMEOUT_SECSกำหนดเวลา timeout สำหรับ subprocess ขณะอัปเกรด

21. การอัปเกรดอย่างปลอดภัย (Upgrades)

bash
# 1. ตรวจสอบเวอร์ชันใหม่
specify self check

# 2. ดูพรีวิวการอัปเกรด (Dry-run)
specify self upgrade --dry-run

# 3. อัปเกรดตัว CLI จริง
specify self upgrade

# 4. อัปเดตไฟล์และเทมเพลตในโปรเจค

specify extension update

22. การแก้ปัญหาที่พบบ่อย (Troubleshooting)

ปัญหาที่พบสาเหตุแนวทางแก้ไข
คำสั่ง Slash commands ไม่แสดงในแชทAgent ยังไม่ได้โหลดไฟล์ skill ใหม่Restart IDE หรือโปรแกรม Agent ทั้งหมด แล้วตรวจดูว่าไฟล์อยู่ในโฟลเดอร์ skill เช่น .claude/skills/ หรือ .github/skills/
ข้อความเตือน directory is not emptyใช้ specify init ในโฟลเดอร์ที่มีไฟล์อยู่แล้วใส่ flag --force และ --here หลังทำ backup หรืองานเดิม
คำสั่ง Slash commands ซ้ำซ้อนมีไฟล์คำสั่งเก่าตกค้างลบโฟลเดอร์ skill เก่าออกแล้วรัน specify integration switch <agent> ใหม่
ไม่ได้ใช้ Git จะทำงานได้ไหมเข้าใจผิดว่าต้องมี Git BranchSpec Kit อ้างอิงจาก feature.json สามารถทำงานได้ปกติแม้ไม่มี Git

23. Interactive Cheat Sheet (ค้นหาแนวทางตามสถานการณ์)

สถานการณ์ที่พบกระบวนการ / คำสั่งที่ต้องใช้เป้าหมาย
เริ่มต้นสร้างโปรเจคใหม่specify init → /speckit-constitution → /speckit-specifyสร้างโครงสร้างและเริ่มวงจร SDD
นำมาใช้กับโปรเจคเดิมที่มีโค้ดspecify init --here --force → ตั้ง Constitution คุมของเดิมจำกัดขอบเขตการแก้ไขเฉพาะ Bounded Change
ความต้องการยังไม่ชัดเจน/speckit-clarifyตอบคำถามเพื่อลดความกำกวมในข้อกำหนด
กำหนด Architecture / Tech Stack/speckit-planเลือกภาษา, เฟรมเวิร์ก, และฐานข้อมูล
ตรวจสอบความสอดคล้องของเอกสาร/speckit-analyzeค้นหา Gap/Conflict ข้ามเอกสาร (Read-only)
ลงมือเขียนโค้ดตามงาน/speckit-implementสร้างโค้ดตามลำดับใน tasks.md
ตรวจสอบว่าโค้ดสร้างครบตามสเปกหรือยัง/speckit-convergeตรวจ Gap และเพิ่ม Task จนได้ผล Converged
แปลง Tasks เป็น GitHub Issues/speckit-taskstoissuesสร้าง GitHub Issues อัตโนมัติจาก tasks.md
มีบั๊กเกิดขึ้นในระบบspecify extension add bug → /speckit-bug-*วินิจฉัย แก้ไข และทดสอบยืนยันผล (verified)
ต้องการประเมินไอเดียก่อนลงทุนspecify extension add assess → /speckit-assess-*ได้ข้อสรุป verdict: go / clarify / kill
ต้องการสลับ AI Agentspecify integration switch <key>เปลี่ยนรูปแบบคำสั่งให้ตรงกับ Agent ใหม่
ต้องการอัปเกรดเครื่องมือspecify self check → specify self upgradeอัปเดต CLI เป็นเวอร์ชันล่าสุด
สรุปย่อใน 1 บรรทัด: specify = นิยามความต้องการ · plan = เลือกวิธีและเทคโนโลยี · tasks = แบ่งงานย่อย · implement = เขียนโค้ด · converge = ตรวจสอบความครบถ้วน
